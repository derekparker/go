## Incident: stale gc-pause-bench binaries in first Candidate 2 attempt

First Candidate 2 build command chained `cd /home/deparker/go-numa && go build -o /tmp/pb/gcpause-base ./numa-design/gc-pause-bench` etc. from the go-numa root. `numa-design/gc-pause-bench` carries its own `go.mod` (separate module), and building it as a relative path argument from a different module's root failed with "go: go.mod file not found in current directory or any parent directory" -- silently, because the multi-line ssh script had no `set -e` and the failure was followed by an unconditional `echo BUILDS-OK`. The two `garbage` builds in the same script (via `go install pkg@version`) succeeded (module-aware install doesn't need a local go.mod), masking the two failed gc-pause-bench builds.

`/tmp/pb/gcpause-base` and `/tmp/pb/gcpause-numa` therefore still pointed at PRE-EXISTING binaries from earlier that day (04:12, mtimes didn't match the fresh garbage builds' 13:55 mtimes -- the giveaway). `go version -m` on the stale `/tmp/pb/gcpause-numa` showed it was built from commit `7ec36777f3` -- predating the entire v3 locality plan and all of Workstream A's confinement code (Tasks 1-3 didn't exist yet at that commit). Confinement could not possibly engage from a binary built before `numaConfineIfSmall` existed.

First Candidate 2 sweep (n=10) ran entirely on this stale binary. Its "C" arm was actually testing old Layer 0/1/2 behavior with no confinement at all, not Workstream A. Result at the time: B vs C not significant (p=0.162), and alarmingly C nominally SLOWER than both B and A -- fully explained once the binary provenance was understood (C had no confinement, so it should behave like B, modulo whatever Layer 2 leftover behavior that commit carried, plus normal run-to-run noise -- it does NOT reflect Workstream A's actual performance).

**Fix:** rebuilt both binaries with `cd .../gc-pause-bench` (module directory) + `GOWORK=off`, verified success explicitly (not just relying on echo), confirmed via `go version -m` (`go1.28-devel_c226071c35 ... X:numa` for the numa build) and mtimes, and confirmed confinement engages via `GODEBUG=numa=1` smoke test ("numa: confined to node 1 cpus 128") before re-running the sweep. Candidate 1's `garbage` binaries were independently verified NOT to have this problem (both `go version -m` showed `c226071c35`/`X:numa` correctly, matching their fresh 13:55 mtimes) -- Gate 6's result stands as originally reported.

Old (invalid) sweep output removed from `/tmp/pb/wsA-cand2` and `/tmp/wsA-cand2-sweep.log` before re-running with the corrected binaries.
